## 2026-07-30 05:40 — [DOMAIN-FIX: domains/validator-engine.md] deterministic vs semantic boundary: three proven over-extrapolations

User-supplied constraint, now binding on this repo: **programs verify determinable low-level facts;
the model judges what those facts mean and what to do next.** A validator may prove ONLY the
condition it actually inspected. Dressing an open/semantic question as a boolean, score, fixed
label, or checklist item creates false certainty and redirects the agent toward form-compliance.

Three violations PROVEN in the current skill (constructed and run, not inferred):

- **R5 is presence-only and is read as completeness.** `checks/nodes.py:28-29` is literally
  `if field not in node`. I built a node carrying all 21 required fields with `title: ""` and
  `preconditions: []` — it PASSES R5. So R5 proves "filled in", while the surrounding docs treat a
  passing plan as structurally complete. Textbook "字段完整 != 信息充分".
  [source: skills/create-loop/scripts/checks/nodes.py:28]
- **`score` is a semantic judgment wearing a number's clothes.** `llm_judge` is defined as "A
  separate LLM scores the node's output against a rubric" — the number is model opinion. No
  validator currently compares `score` to `threshold`, and **that absence is CORRECT**. Adding the
  comparison would give a fabricated number deterministic authority over completion. I had planned
  exactly that (T2.3) and have now cancelled it; the right fix for judged gates is provenance
  (the assurance axis), never arithmetic on an opinion.
  [source: skills/create-loop/references/evidence_gates.md:126]
- **`INTEGRITY OK` over-claims in its NAME.** It verifies cross-file reference consistency; the
  string asserts whole-loop integrity. Naming is itself an over-extrapolation — a rule whose name
  implies more than it inspected is a defect even when its logic is right.
  [source: skills/create-loop/scripts/check_loop_integrity.py:159]

Non-obvious consequence worth keeping: the fix for R5 is NOT a non-empty check. A non-empty
`preconditions` is not a *correct* `preconditions` — that just moves the same error up one level.
The fix is to bound R5's claim in its message and state in the docs that presence is not
sufficiency, leaving adequacy to the runner's recorded judgment.

Standing rule adopted: every validator must state the exact fact it inspects AND the conclusion it
does not license. Six-part keep test (definable+stable / directly inspects the fact / conclusion
not extrapolated / triggers a clear action / error risk acceptable / genuinely better than model
judgment) — fail any one and it may not decide state, certify completion, or dictate next steps.

Also captured: the `event_log` vs `checkpoint` authority contradiction. `recovery_protocol.md:340`
+ the event_log schema both declare the log PRIMARY with every other file a projection of it, but
`SKILL.md:577` opens Mode C (blank-session resume) with "The checkpoint is the only source of
truth", and `state_model.md`'s 9-step resume never replays the log at all (0 mentions). Compounding
this: the log has only 4 event kinds (pre_effect/post_effect/note/mutation) and NO approval or
blocked event, so `pending_approvals`, `blocked`, and `open_assumptions` are NOT reconstructible by
replay — §3.2.2 confirms it by listing only node_states/cost_units_spent/iteration/attempt as
recomputable. The checkpoint therefore cannot become derived-only without silently losing pending
